# Specification: Distributed Job Queue Service

Status: Draft with binding engineering and Docker E2E requirements; not yet published to an issue tracker. Implementation and verification are pending.

## Problem Statement

Clients need to submit asynchronous work without waiting for execution and then understand whether it is waiting, running, completed, failed, or cancelled. They need scheduling, priority, retries, progress, and an audit trail without accidentally creating multiple jobs when repeating a submission.

The engineering assessment also needs demonstrable behavior when workers crash, publication is interrupted, services restart, or several workers and API instances run concurrently. Persistent state must remain understandable and correct even when transport redelivery repeats physical execution. The solution must remain small enough to run, inspect, and explain locally.

## Solution

Provide a Python 3.11+ FastAPI service with Postgres 16 as its authoritative state store and RabbitMQ 4.3 for durable work distribution and status events. Clients use authenticated HTTP endpoints to submit, inspect, list, cancel, and retry jobs. Identical, independently running workers execute four asynchronous mock handlers: email, webhook, report, and batch.

The API owns every database operation, including dispatch, status application, recovery, and audit history. Workers communicate through RabbitMQ and have no database access. A shared work queue distributes normal deliveries among workers; one active sequential status consumer applies execution events.

The service offers automatic retries with backoff, one optional manual retry cycle, cancellation before dispatch, recovery of uncertain publication and abandoned processing, and durable ordinary restart behavior. Its execution guarantee is at least once with guarded persistent state. Documentation and tests explain the accepted duplicate-execution window and exercise-level operational limits.

Build this simply and effectively. SOLID and DRY are mandatory, expressed through clear responsibilities, small necessary interfaces, and one authoritative implementation of each business rule. Overengineering, speculative abstractions, duplicated policy, filler code, and excessive unit testing are prohibited. Write comprehensive adversarial E2E tests before the corresponding implementation. Passing those tests against the deployed Docker services is the success metric and completion gate.

## Implementation Decisions

1. **Ownership and topology.** Build an HTTP API with API-hosted scheduler/publication recovery, status consumer, reaper, DLQ consumer, and cleaner, plus an independent shared worker service. All Postgres access belongs to the API side. Workers receive broker credentials but no database connection configuration and perform no HTTP execution-admission handshake.

2. **Durable messaging.** Use one durable quorum work queue, `q.jobs`, a durable status queue, `q.job-status`, and one work dead-letter queue, `q.jobs.dlq`, reached through `dlx.jobs`. All workers consume the same work queue and support all four handlers. Enable Single Active Consumer for the status queue; use ordinary competing consumers for work. Persist work/status messages and use publisher confirmations.

3. **Authoritative model.** Persist jobs and associated audit logs. A job contains its UUID, type, validated payload, lifecycle status, priority, result/error, progress, cycle and lifetime attempt counts, maximum attempts, manual-cycle usage, scheduling, idempotency key, dispatch identity and publication recovery state, lifetime and attempt-local timing, and creation/update/terminal timestamps. Audit logs carry level, message, structured metadata, timestamp, and applicable cycle/attempt/token context. Exact DDL, constraints, migrations, and indexes remain execution-planning work; indexes must support due selection, publication recovery, expired processing, listings, and ordered logs.

4. **Lifecycle and guards.** Support `scheduled`, `pending`, `dispatched`, `processing`, `completed`, `failed`, and `cancelled`. `dispatched` means reservation has committed, including an unconfirmed publication. Guard transitions by current state and, for execution events, current token. Invalidate a token when its attempt ends or is abandoned. A completed or cancelled job cannot be reopened by execution events; failed jobs reopen only through their one permitted manual retry. State changes and corresponding audit writes share a transaction.

5. **Submission contract.** `POST /jobs` accepts type, payload, priority, optional `scheduled_for`, optional `idempotency_key`, and `max_attempts`. Defaults are priority 4, immediate eligibility, no key, and three attempts. Accept priorities 0–31 and attempt budgets 1–5. Validate payloads by type, reject empty/overlong supplied keys, and require timezone-aware supplied timestamps. Future work starts scheduled; immediate or past-dated work starts pending. New work returns HTTP 202 with ID and initial status. Exact input-size limits and error envelopes remain planning decisions.

6. **Submission idempotency.** Enforce optional-key uniqueness in Postgres, including concurrent requests. A duplicate returns HTTP 200 with the existing ID, current status, and `deduplicated=true`; it does not update any submission attributes. Retain keys at least 24 hours, never release an active job's key, and allow best-effort release on terminal jobs older than 30 days. Submission deduplication provides no execution-deduplication guarantee.

7. **Read contracts.** Provide `GET /jobs/{id}`, `GET /jobs`, and `GET /jobs/{id}/logs`. Expose state, payload, result/error, progress, attempt counters, manual-cycle usage, scheduling, and public timestamps. Internal dispatch tokens and recovery fields need not be public. Lists filter by status/type and use limit/offset pagination with `items`, `limit`, `offset`, and `total`; default limit 50, maximum 100. Sort jobs by creation descending with ID as tie-breaker and logs chronologically with log ID as tie-breaker. Unknown jobs return 404.

8. **Cancellation contract.** `POST /jobs/{id}/cancel` changes only scheduled/pending jobs to cancelled and returns HTTP 200. All other states return 409. Cancellation and scheduler reservation use guarded database transitions: a committed cancellation prevents dispatch; a committed reservation prevents cancellation even if publication has not completed.

9. **Initial dispatch.** On a nominal two-second tick, atomically reserve due scheduled/pending jobs using short database claims such as row locking with skip-locked semantics. Order eligible jobs by descending priority, ascending eligibility time, and a stable tie-breaker. Assign a new claim token, persist dispatch and recovery timing, and commit before publishing. No database transaction spans publication or execution. Ordinary pickup excludes dispatched and processing jobs. The tick is a pickup target, not a latency SLA.

10. **Publication recovery.** The job row records confirmation and future recovery eligibility; do not add a separate outbox subsystem. Failed or uncertain publications remain outstanding and are retried with the same token after a bounded delay. Reserve recovery atomically across API instances. Confirmed dispatches are not routinely republished or expired because workers are offline or queues are backed up. Confirmation recording is guarded so it cannot overwrite execution that has already advanced. Broker acceptance followed by a crash before recording confirmation can cause duplicate publication; this is accepted.

11. **Work contract and acknowledgement order.** Work messages carry job identity, type, payload, priority, claim token, and sufficient cycle/attempt context. Each worker has one outstanding work delivery, dispatches by type, confirms its processing publication before invoking the handler, confirms final-outcome publication before acknowledging work, and publishes ordered events on the same channel. A business failure is a handled delivery and is acknowledged after its failure event is confirmed. The API schedules business retries. Confirmation proves broker acceptance, not application of the event in Postgres.

12. **Status application.** One active consumer processes status events sequentially and acknowledges each only after its database transaction commits. Every execution event requires job identity, claim token, event/outcome type, and applicable result/error/progress. Duplicate processing cannot count an attempt twice; duplicate accepted transitions cannot duplicate their audit entries. Stale tokens cannot change a newer attempt. Preserve a valid current-attempt terminal outcome even if its start has not yet been applied after reconnect/recovery. The precise small retry/transition mechanism for this case and the concrete message schemas remain planning decisions; do not add an event store.

13. **Logical attempts.** Allocate a new token per new logical attempt; uncertain publication and broker redelivery reuse the existing token. Increment both `attempts` and `total_attempts` once when processing is first accepted for that token. A pre-start failure can leave both unchanged. Reset progress and attempt-local timing for a new logical attempt; clear current execution output/error when execution starts. Preserve the latest failure through automatic backoff. Preserve the first lifetime start across cycles. Counters describe logical attempts, not physical handler invocation counts.

14. **Automatic retry.** Transient failure and timeout return processing to pending with backoff while its current cycle has budget; otherwise they produce failed with a terminal timestamp. Permanent failures end the cycle immediately. Default retry waits are 30 seconds after the first failed attempt and 120 seconds after the second; continue the same exponential progression for budgets up to five. Preserve priority and use the same logic with shortened timing configuration in tests. Redelivery of an existing token grants neither another business attempt nor another backoff cycle.

15. **Manual retry contract.** `POST /jobs/{id}/retry` returns HTTP 202 and pending only for a failed job whose manual cycle is unused. Reset current-cycle attempts to zero, set manual-cycle usage, clear result/error/progress/terminal and attempt-local dispatch state, and make the job immediately eligible. Preserve submission identity, payload, priority, lifetime attempts, original first start, and logs. Ignore the original schedule for this new cycle. Reject other states and every second manual retry with 409, including when the manual cycle ended early. A default-budget job has at most six logical attempts across both cycles.

16. **Mock handlers.** Use asynchronous mocks with no external effects. Email validates a recipient, delays 1–3 seconds, and returns a stable job-derived message ID. Webhook validates an HTTP(S) URL, delays 1–2 seconds, and normally simulates 80% success/20% transient failure, returning a mock status code on success. Report accepts a parameters object, delays 3–5 seconds, and returns a stable job-derived file URL. Batch processes an items list with small per-item delays and returns a processed count and summary; empty input succeeds with an empty summary. Final payload shapes and modest limits remain planning work.

17. **Progress and test controls.** Apply progress only to the current processing token, never decrease it within an attempt, and set it to 100 on completion. It may reset for another attempt, and polling need not observe every intermediate update. Provide deterministic mock controls such as failure for the first N lifetime logical attempts followed by success, plus controllable delays. These enable repeatable retry/timeout tests through real behavior without modifying the original payload; exact control configuration remains planning work.

18. **Priority boundaries.** Apply priority at eligible-job selection and broker delivery using the agreed RabbitMQ 4.3 quorum priority behavior. Suggested levels are 0 low, 4 normal, 15 high, and 30 critical. Promise preference among eligible same-type jobs still awaiting dispatch/delivery. Do not promise preemption, cross-type execution order, per-type capacity, fairness, or priority aging. Priority never bypasses scheduling/backoff, and recovery redelivery can have different ordering.

19. **Timeout and reaper.** Worker timeouts are 15 seconds for email/webhook, 60 seconds for report, and 180 seconds for batch. Timeout is a transient failure. A nominal ten-second reaper poll uses attempt start plus type timeout and a small recovery allowance; progress and general row modification do not renew it. Recheck state, token, and expiry atomically before abandoning the attempt. Invalidate its token, log recovery, and schedule backoff or final failure according to budget. A concurrent completion must not be overwritten. Recovery is eventual, and a disconnected worker can still execute after abandonment.

20. **Dead-letter handling.** An API-side consumer handles the work DLQ. Malformed work and appropriate infrastructure failures can be dead-lettered. A matching current dispatched/processing job becomes failed with a useful error and atomic audit record; stale messages cannot change a newer attempt or accepted terminal outcome. If status publication fails while the work channel is usable, rejecting without requeue can dead-letter work; connection loss instead leaves normal unacknowledged-delivery recovery. Select a small delivery limit compatible with crash tests during planning. Accept that transient infrastructure faults can require manual retry; provide no automatic replay or lossless transfer guarantee.

21. **Failure supervision and shutdown.** Use asyncio for the I/O-bound workload. Expected dependency failures reconnect with bounded backoff; unexpected programming errors are logged and fail the service visibly. Workers stop accepting work, finish the current bounded handler, publish its final event, acknowledge, and close connections. Shutdown allowance must exceed the longest supported handler timeout plus publication time. The API stops scheduling and finishes current transactions and committed-event acknowledgements before closing. Final worker events remain durable if the API exits first. Forced shutdown follows ordinary crash recovery.

22. **Health and security.** All job routes require an environment-configured fixed bearer token; health is unauthenticated. Apply configurable per-process submission/retry rate limits. Use consistent 401/422/429 errors. Health reports database/broker connectivity, job counts by state, ready/unacknowledged work, connected work consumers, status depth, and DLQ depth. Return 503 for required dependency failure; management-statistics failure alone or zero consumers yields degraded reporting rather than claiming those dependencies are unreachable. Missing statistics are marked unavailable. Connected consumers do not prove handler health. Exact rate limits, environment names, and health/error schemas remain planning work.

23. **Logging and cleanup.** Emit structured JSON logs with component and applicable job/type/cycle/attempt/token context. Persist lifecycle audit records atomically with transitions regardless of which API-side component makes them. Keep attempt history in structured job logs, with detailed handler output permitted on stdout. Perform hourly best-effort cleanup in small batches using a 30-day threshold for old logs and eligible terminal-job keys. Job rows can remain indefinitely; cleanup is not an archive or bounded-storage guarantee.

24. **Deployment and documentation.** Docker Compose runs the API, a scalable shared worker service, Postgres, and a broker pinned to the chosen 4.3-compatible behavior. Persist both dependency stores, supply readiness and reconnect behavior, and initialize schemas repeatably. Run application containers as non-root, keep secrets out of source control, expose only the API outside the Compose network, and give database credentials only to the API. One broker user is sufficient locally. Provide a multiple-worker demonstration and a working multiple-API test arrangement without host-port conflicts. Document setup, authenticated submission, tests, scaling, architecture, agreed tradeoffs, one improvement with more time, and specific useful and incorrect AI contributions. Exact Compose setup, migration tooling, and routing are planning decisions.

25. **Simplicity is a binding constraint.** Implement the smallest clear design that satisfies the agreed behavior and Docker E2E acceptance tests. Every module, class, abstraction, dependency, configuration switch, and background mechanism must have a current requirement or concrete simplification that justifies it. Prefer direct functions and composition when sufficient. Do not add generic repository frameworks, base-class hierarchies, plugin systems, custom dependency-injection containers, internal event buses, speculative extension points, or extra services for hypothetical future needs. Complexity required for correct transactions, delivery, and recovery must remain explicit; simplicity cannot weaken a required guarantee.

26. **Apply every SOLID principle pragmatically.** Single responsibility: give HTTP handling, lifecycle policy, persistence, broker transport, and mock execution clear responsibilities; avoid handlers that also own recovery or persistence. Open/closed: keep type-specific handler behavior behind the existing common handler contract rather than scattering type switches through scheduling and state updates; do not build a plugin framework. Liskov substitution: every handler must honor the same execution, result/error, timeout, and progress contract where applicable. Interface segregation: give each consumer only the operations it uses, without broad service objects. Dependency inversion: keep retry/lifecycle rules independent of HTTP and broker-client plumbing, wiring necessary concrete dependencies at startup. Functions, plain data, and small modules can satisfy these principles; an interface, abstract base class, and wrapper for every object cannot be justified by SOLID alone.

27. **DRY applies to knowledge and policy.** Maintain one authoritative definition of lifecycle states, transition guards, retry/backoff calculation, attempt accounting, timeout policy, message contracts, validation rules, and state-plus-audit transaction behavior. Reuse these rules across API-side components rather than allowing the scheduler, status consumer, reaper, and DLQ consumer to drift. Transport parsing can be separate from HTTP parsing, but neither should reimplement lifecycle policy. Extract shared code when it represents the same rule or responsibility; do not combine unrelated behavior merely because a few lines look alike. Keep test expectations independent: derive expected outcomes from this specification, not by calling the production rule being tested.

28. **No slop or defensive scaffolding.** Use concrete names, readable control flow, explicit transaction and acknowledgement boundaries, validated configuration, and useful contextual errors. Remove dead code, unused options/dependencies, duplicate wrappers, stale comments, and placeholders before calling a slice complete. Comments explain a non-obvious invariant or tradeoff rather than narrating the code. Catch errors where a recovery action is defined; do not swallow exceptions, silently report success, or add broad retry loops that hide bugs. Do not implement behavior beyond this specification to make the architecture appear more elaborate.

29. **Tests drive vertical delivery.** For each execution slice, first specify its observable acceptance outcomes in runnable Docker E2E tests, then establish a meaningful failing result, implement the minimum coherent behavior to pass, and refactor while preserving green tests. Do not build the entire application first and retrofit tests afterward. Keep production mechanisms and the test harness small; use deployed-service fault injection and existing mock controls instead of building a testing platform. A passing unit suite, high line coverage, or a manual happy-path demonstration cannot substitute for the required deployed E2E evidence.

## Testing Decisions

These requirements are binding. The user's chosen success metric is comprehensive, adversarial E2E behavior against deployed Docker services, with tests written first. No application or test code exists yet, so there is no existing test prior art to reuse. The PRD acceptance scenarios, agreed design decisions, and the requirements below define the coverage.

1. **Success metric: deployed Docker E2E tests.** Build and run the actual API, worker, Postgres, and RabbitMQ services through Docker Compose. Drive the published HTTP API over the network from a separate test process or test container; use real broker connections and container lifecycle controls where the scenario requires them. Exercise the same application images, entrypoints, migrations, queues, and execution paths used by the documented local deployment. Dependency mocks, in-process HTTP clients, direct calls into application code, and host-only worker runs do not qualify as E2E acceptance evidence. Timing configuration may be shortened, but must use the same business logic and infrastructure.

2. **Write tests first and demonstrate meaningful red.** For each slice, write the required E2E scenarios and assertions before implementing the associated application behavior. Establish minimal working deployment/test plumbing, then show that the scenario fails because required behavior is missing or wrong. A syntax error, missing test dependency, or unreachable test runner is not evidence of a meaningful behavioral failure. Implement until the tests pass, then simplify under those tests. Record the initial relevant failure and final passing command/result in the slice's execution evidence. Tests may evolve when a contract is deliberately clarified, but must not be weakened to accommodate a bug.

3. **Avoid excessive unit testing.** The default is deployed E2E coverage. Prove worker acknowledgement order, timeout behavior, and shutdown through broker-visible outcomes and container behavior wherever possible. Add a focused unit or component test only for a specific important invariant that the deployed scenarios cannot reliably or economically establish, and state that gap. Do not duplicate E2E coverage across layers, test getters or trivial wrappers, assert private calls, mock every collaborator, or pursue a coverage percentage. Supporting tests supplement the Docker E2E gate and never replace it.

4. **Good tests assert behavior and invariants independently.** Use public response contracts, durable state visible through API reads/logs, broker-visible outcomes, and bounded eventual completion. Assert exact outcomes where the contract is exact and the permitted outcome set where a race legitimately has multiple winners. Avoid assertions about helper structure, exact SQL, private methods, or scheduler iteration counts. Expected retry times, counts, transitions, and errors come from the specification rather than production helpers. Use deadline-based polling and deterministic mock outcomes instead of long arbitrary sleeps or statistical webhook outcomes. Polling must fail with the last observed state when its deadline expires.

5. **Core API scenarios include hostile inputs and boundaries.** Submit and complete all four types; assert correct mock result shapes, missing-ID errors, stable pagination/filtering, audit order, empty-batch success, token authentication, rate limits, and dependency/degraded health behavior. Cover missing/wrong credentials, malformed JSON, unknown types/states, invalid type-specific payloads, naive timestamps, empty/overlong keys, pagination limits, and the allowed/disallowed boundaries of priority and attempt budgets. Verify rejected requests create no jobs. Observe nondecreasing batch progress within an attempt and final progress 100 without requiring every intermediate percentage to be visible by polling. Distinguish database failure, broker failure, unavailable management statistics, and zero consumers in health assertions.

6. **Idempotency and cancellation scenarios exercise real races.** Release concurrent same-key HTTP requests together and assert one job and unchanged submission attributes, including differing duplicate payloads; repeat after state advances and assert current-state deduplication. Race concurrent manual-retry requests and assert only one fresh cycle is granted. Exercise scheduled/pending cancellation and race cancellation against dispatch, allowing only the documented winner outcomes. A successful cancellation must remain cancelled without handler execution; a committed dispatch makes cancellation return 409. Confirm future jobs never dispatch early, including at high priority. Use controlled service/worker startup where a specific waiting state is needed and bounded repeated runs for contention cases rather than assuming one lucky execution proves safety.

7. **Retry and timeout scenarios exhaust the budgets.** Use deterministic failure-then-success behavior to verify automatic backoff, permanent failure, timeout, budgets of one, the default three, and the maximum five, one fresh manual cycle, lifetime-history preservation, immediate manual eligibility, and rejection of a second manual retry. Assert errors stay visible in backoff, execution output clears at the specified boundary, progress can reset between attempts, and successful manual retry requires no payload mutation. Assert retries cannot run before eligibility, retain priority, stop at budget exhaustion, and count duplicate starts only once. Observe the terminal job beyond the next possible retry window to detect accidental additional work. Permanent failure must reject a second manual cycle even if its allowed manual cycle used only part of its budget.

8. **Priority and concurrency scenarios use deployed replicas.** Queue eligible jobs of the same type before enabling consumption, then verify priority preference without asserting preemption. Separately run several worker containers and verify overlapping normal processing of distinct deliveries, with one outstanding work delivery per worker and no ordinary duplicate pickup. Run multiple API containers and demonstrate safe scheduler claims and one active sequential status consumer; terminate the active consumer and verify failover. Distinguish ordinary-delivery observations from failure cases where duplicate physical execution is accepted.

9. **Dispatch recovery scenarios target the failure windows.** Keep workers stopped across scheduler ticks and verify confirmed queued work does not multiply. Interrupt the API after committed reservation but before publication, and separately after broker acceptance but before recorded confirmation; restart and verify eventual recovery with the same logical attempt identity. Exercise competing recovery schedulers and late confirmation without execution-state regression. Do not require duplicate-free physical execution when publication acceptance was uncertain. Where normal container control cannot reliably reach the boundary, use a narrowly scoped, explicitly enabled test hook that pauses or fails the real path; do not replace database/broker operations or build a generic fault-injection framework.

10. **Event and audit resilience scenarios challenge state guards.** Publish controlled duplicate/stale events and dead letters through the real broker, then observe API state and logs. Verify attempts and accepted transition logs are not duplicated, progress cannot regress or overwrite terminal state, old tokens cannot affect newer attempts, and stale DLQ messages cannot fail accepted outcomes. Include a valid current-token terminal event whose start has not yet been applied and verify its outcome is preserved. Exercise malformed work, missing-token status events, and a valid message afterward; invalid messages must not mutate a job or permanently block useful consumption. Restart status consumption before commit and after commit/before acknowledgement, verifying atomic state/audit and no lost accepted result. Assert eventual outcomes as well as the absence of forbidden state changes; absence alone can hide a stalled consumer.

11. **Crash and reaper scenarios cover distinct recovery mechanisms.** Kill a worker before processing publication, during execution after accepted start, and after final publication but before work acknowledgement. Assert the contract appropriate to each window, allowing redelivery and repeated physical execution where documented. Separately hold an attempt stale long enough to exercise the reaper explicitly; do not assume it always beats redelivery. Verify continuing progress does not extend expiry, the abandoned token cannot update the successor, and guarded recovery cannot overwrite concurrent completion. Include a failure before accepted start to verify counters need not increase. Every accepted job must reach a contractually valid eventual outcome within a bounded test deadline rather than merely survive a restart.

12. **Shutdown and persistence scenarios use actual container lifecycle operations.** Verify graceful shutdown completes a bounded current job, publishes its result, acknowledges work, and stops new intake. Test API exit before final worker status and later status recovery. Force termination separately and apply crash-recovery expectations. Restart API, workers, broker, and database while retaining their test volumes; verify accepted jobs, committed audit history, and durable queued work resume without reset or reseeding. Distinguish ordinary restart from destructive volume loss. Verify reconnect behavior after a temporary dependency outage and that another job succeeds after recovery.

13. **Housekeeping and deployment checks.** Verify eligible old logs/terminal keys can be cleaned without releasing active or too-young keys, using narrowly scoped aged fixtures where needed. Confirm documented Compose startup from empty test volumes, worker scaling, the multiple-API arrangement, repeatable schema initialization, and credential/network boundaries. Cover each required acceptance behavior and relevant failure boundary, while avoiding redundant permutations, unrelated stress benchmarks, or an exhaustive distributed fault matrix.

14. **Keep the harness small, isolated, and diagnostic.** Share only concrete harness responsibilities: HTTP calls, deadline polling, Compose/container control, broker observation/injection, and failure diagnostics. Do not recreate the scheduler or lifecycle engine in tests. Isolate runs with dedicated Compose project names, credentials, volumes, and test data; cleanup must affect only the run's resources. Wait for explicit readiness, distinguish initial startup from expected in-scenario outages, and use bounded waits throughout. On failure, retain or capture test name, job IDs, last responses, relevant service logs, container states, and queue statistics with secrets redacted. Fault hooks and shortened timings must be explicitly enabled for tests and inactive in ordinary deployment.

15. **Completion gate and evidence.** Provide one documented reproducible command that builds/deploys the test stack, establishes readiness, runs the complete required Docker E2E suite, reports failure with a nonzero exit code, and cleans up the run's resources after collecting diagnostics. A new behavior passes its tests before its slice is complete; the complete suite must pass against images built from the final source before the feature is declared done. Track acceptance requirements to concrete scenarios with a small checklist; no requirement is satisfied by a test name without assertions. Report command, source revision or tested build identity when available, scenario results, and any remaining gaps. Do not silently skip required cases, blanket-retry failed tests until green, weaken race assertions, or substitute coverage statistics. Fix the cause of flaky tests.

16. **Limits of evidence.** Stable mock result IDs, attempt counters, and accepted audit records do not prove exactly-once physical execution. Use direct worker/broker observations when assessing normal delivery or acknowledgement behavior, and explicitly allow repeated physical execution in documented failure windows. Brutal tests mean deliberate, reproducible attempts to break each promised guarantee; they do not expand the product's guarantees beyond the accepted scope.

## Out of Scope

- Real email delivery, outbound webhook requests, external report storage, or other real side effects.
- Workflows, DAGs, cron scheduling, per-tenant isolation, user accounts, JWTs, or authorization scopes.
- Cancellation after dispatch, broker-message deletion for cancellation, execution-admission RPCs, and worker access to Postgres.
- Exactly-once execution/effects, absolute prevention of overlapping execution during failures, a general execution-deduplication service, a separate outbox subsystem, or an event store.
- Per-type worker fleets/work queues, cross-type ordering promises, per-type capacity reservation, preemption, priority aging, fairness guarantees, and starvation prevention.
- Heartbeat infrastructure, a separate infrastructure-retry framework, automated DLQ replay, or guaranteed lossless DLQ transfer.
- Globally coordinated rate limiting, production identity/authorization, and per-service broker identities.
- Database partitioning/sharding, broker clustering, production high availability, permanent disk/volume-loss recovery, and claims that a single-node quorum queue is a replicated deployment.
- Production retention guarantees, archival of history, deletion of all old job rows, or bounded total storage.
- A user interface, production monitoring platform, benchmark program, or exhaustive distributed fault matrix.
- Speculative architecture/frameworks, unnecessary layers or dependencies, duplicated business policy, boilerplate-only abstractions, and excessive or implementation-coupled unit testing. Test line coverage is not an acceptance target.
- Implementation code, concrete SQL/DDL, final message/error schemas, exact configuration names and limits, migration tooling, module/file ownership, and vertical execution slices in this specification. These remain the subsequent execution plan's responsibility.
